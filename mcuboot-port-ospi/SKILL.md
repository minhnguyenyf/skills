# rm_mcuboot_port and the `ra8_ospi` test project

## Folder map (`ra/fsp/src/rm_mcuboot_port/`)
- `rm_mcuboot_port.c`: `RM_MCUBOOT_PORT_BootApp()` sets VTOR, handles dual-bank swap (reset or boot-without-reset), calls `rm_mcuboot_cleanup()`, then a naked `start_app(pc, sp)` (MSR MSP; BX). Disables MSPLIM / SP monitor first.
- `flash_map.c`: MCUboot flash backend (`flash_area_open/read/write/erase/align`, `flash_area_get_sector(s)`, flush, cleanup). Picks driver by feature macro: MRAM, FLASH_HP, else FLASH_LP. Internal flash is memory mapped; writes smaller than the write alignment are buffered in RAM and flushed (`RM_MCUBOOT_PORT_BUFFERED_WRITE_ENABLE`, off for plain overwrite-only). Two flush buffers indexed by `fa_device_id >> 7` (internal=0, external=1). Flush-buffer `g_current_block` is set at runtime because the bootloader never runs the C-library scatter loader, so `.data` initializers are not applied.
- `.module_descriptions/`: 4 modules: `rm_mcuboot_port`, `rm_mcuboot_protected_mode` (SCE9 custom crypto in `custom_crypto_stacks/protected_mode/`), `rm_mcuboot_ext_memory_qspi`, `rm_mcuboot_ext_memory_ospi_b`.
- `!dsn/module.xml`: pack-creator input (sources + include folders per module; QSPI and OSPI_B modules ship no files, config only). `!dsn/rm_mcuboot_port_usage_notes.md`: user doc plus internal `@anchor um_mcuboot_port_ospi_*` trace tags.
- `!test/` (dev unit test build: `rm_mcuboot_port_test.c`, `rm_mcuboot_port_data.c`, `.rkey` keys, `flash_with_key_*.sh`), `!test_app/` (app-side tests TG1/TG2, MMF, dual bank, secondary/primary debug images), `.xml_tests/` (e2 studio project-creation tests: encryption, dxip_mmf, dualbank_tz, macros, pqc).

## OSPI_B external memory (RA8)
- Module `config.middleware.mcuboot_ext_memory_ospi_b` generates `mcuboot_ospi_b_config.h` with `RM_MCUBOOT_PORT_CFG_OSPI_B_CHANNEL` and `RM_MCUBOOT_PORT_CFG_XSPI_BLOCK_ERASE_SIZE` (options 32K/64K/128K/256K, default 32K; guarded by `#ifndef` so a project macro can override). Constraint: channel must equal the channel of the added OSPI_B stack. It defines `gp_mcuboot_xspi_ctrl/cfg/instance` from the OSPI_B stack name, and sets memory accumulator `BOOTLOADER_SECONDARY_USE_OSPI_B`.
- `flash_map.c` is enabled by `RM_MCUBOOT_PORT_CFG_SECONDARY_USE_XSPI` (test project also defines `..._USE_OSPI_B`). The user (or test setup) must call `R_OSPI_B_Open()` before `boot_go()`; the port never opens it. After a secondary image is loaded the target must be reset before MCUboot sees it.
- **Virtual sectors:** MCUboot needs identical sector sizes for both slots, so with XSPI both slots report `RM_MCUBOOT_PORT_VIRTUAL_SECTOR_SIZE = XSPI block erase size`; internal flash erases several native blocks per virtual sector. `flash_area_erase` on the external device returns `FSP_ERR_INVALID_SIZE` unless length and address are multiples of the block size, and polls `statusGet` (huge timeout counter) before/after each erase. Slot sizes must be multiples of that size; the swap scratch area must equal the OSPI erase block (huge), so put scratch in OSPI or use overwrite mode. Erase size must be one the flash supports (S28HL512T: 4KB/256KB; IS25LX512M: 4/32/64/128KB).
- XSPI writes go page by page (`page_size_bytes`), alignment = page size; XSPI flush buffer is 256 words.

## `ra8_ospi` project (`projects/rm_mcuboot_port.xml`, ~line 2788; active, outside every `<?ignore ... ?>` block)
- type `boot`, board `ra8d1_ek`, depends on `rm_mcuboot_app`, crypto = RSIP-E51A plain key with the **v3** `rm_psa_crypto` + `ra/arm/mbedtls` (not TF-PSA-Crypto), `MBEDTLS_CONFIG_FILE=rm_psa_crypto_cfg.h`, littlefs/PSA storage macros on, heap 0x20000, stack 0x4000.
- `test_info_init` points to `ra/fsp/src/r_ospi_b/!test/SetupOSPI.JLinkScript`: `HandleBeforeFlashProg()` power-cycles the OSPI flash (PWR_S toggle and P1_06 reset pulse) because the J-Link loader can't detect it otherwise.
- test macros: `FSP_TEST_FUNCTION=RunAllRM_MCUBOOT_PORTTests`, `TEST_MCUBOOT=1`, `RM_MCUBOOT_PORT_CFG_SECONDARY_USE_XSPI/_OSPI_B`, `RM_MCUBOOT_PORT_CFG_XSPI_BLOCK_ERASE_SIZE=262144` (256KB), `OSPI_B_CFG_COMBINATION_FUNCTION=64BYTE`, prefetch on, DOTF off; main macro config adds `OSPI_B_CFG_DMAC_SUPPORT_ENABLE=0`. `r_ospi_b.c` is a main (instrumented) dir.
- Tests (`!test_app/rm_mcuboot_port_tests_*.c`): TG1 runs `TC_Vtor` only when NOT OSPI (skipped with OSPI), plus multi-image if enabled. TG2 (OSPI only, needs `RM_MCUBOOT_PORT_SECONDARY=1`, else `TEST_FAIL_MESSAGE("Primary app running, expected secondary.")`): virtual sectors match physical block, erase one block, erase multiple blocks, partial erase does not over-erase, rejects unaligned length, rejects unaligned address (requirement ids `mcuboot_port_ospi_*`, Jira FSPRA-4851).
- `!test/rm_mcuboot_port_data.c` (OSPI branch, S28HS512T on EK-RA8D1, **device 1 / CS1**): defines `g_ospi_b_cfg` (1S-1S-1S commands) and `rm_mcuboot_port_ospi_test_setup()`: configures OSPI pins, releases CS0, pulses flash RESET# (P1_06) to leave octal/DDR mode, enables OCTACLK from main osc if disabled (else reads return 0xFF), opens OSPI_B once, then reads JEDEC ID into debug globals `g_ospi_jedec_id` (expect 0x001A5B34).

## `ra6_qspi` project (EK-RA6M5, QSPI secondary slot) added 2026-10-07, NOT yet built or run on hardware

- Why a separate app xml (decided 2026-10-07 after trying the overwrite): `ra6m5_std` (internal-flash secondary, default `boot` linker) depends on the `ra6m5_ek` entry of `rm_mcuboot_app.xml`, a legacy QSPI-flagged app (`..._USE_QSPI=1` only; no boot project used QSPI since the 2022 removal of `ra6m4_qspi`). Overwriting that entry for QSPI breaks `ra6m5_std`, and a second `ra6m5_ek` entry in the same file collides (app build output and flashing are keyed by xml file name + board + toolchain in `SConstruct _add_dependency`, not project name). So QSPI app lives in `rm_mcuboot_app_qspi.xml`, like `rm_mcuboot_app_xip.xml`. Overwriting was tried and reverted at the user's request; keep `ra6m5_std` unless the user decides to drop it. Merging the QSPI entry as a second `ra6m5_ek` entry in `rm_mcuboot_app.xml` was also tried (2026-10-07) and verified broken: `scons -n --build=rm_mcuboot_port --board=ra6m5_ek --project=<either> --compiler=gcc` fails with "Two environments with different actions were specified for the same target ... build_rm_mcuboot_app_typical_debug" for BOTH `ra6m5_std` and `ra6_qspi`. Only options that avoid it: separate app xml (current), or overwrite the single entry and drop `ra6m5_std`.
Dry-run recipe: `export PATH=/opt/arm-gnu-toolchain-13.2.Rel1-x86_64-arm-none-eabi/bin:$PATH; scons -n --build=<module> --board=<board> --project=<name> --compiler=gcc` (also real builds work; toolchains under /opt).
- Linker: ra6m5 `boot`/`image` put the secondary slot in INTERNAL flash at 0x40000 (flash_map entry for `FLASH_AREA_0S_ID` is `FLASH_DEVICE_INTERNAL_FLASH`). The `*_qspi` copies (byte-identical except `memory_regions.*` and `bsp_linker_info.h`) set `__BL_0_S_H_START=0x60000000`, `__BL_0_S_I_START=0x60000200`, shrink the QSPI_FLASH region to 0x60020000/0x1FE0000 so it does not overlap, and mark the secondary flash_map entry `FLASH_DEVICE_EXTERNAL_FLASH`. Slot = 0x20000 = 4 x 32KB virtual sectors, scratch `__BL_S` internal 0x8000. Precedent for variants: `boot_mmf`/`image_mmf`/`image_xip`, selected via `<linker_includes><path>` in the project xml.
- Flow: secondary app is srec-loaded to internal 0x40000 (`secondary_slot`), the bootloader's `TEST_MCUBOOT` hook (`test_files/src/r_tests_runner_main.c` -> `qspi_test_setup_common` in `!test/rm_mcuboot_port_test.c`) erases QSPI and copies 0x20000 bytes there before `boot_go()`; MCUboot then reads the secondary from QSPI. Both projects need `..._USE_QSPI=1` AND `..._USE_XSPI` AND `..._XSPI_BLOCK_ERASE_SIZE=32768`; since FSPRA-4851 `flash_map.c` only compiles external-flash code under `_USE_XSPI`, so `_USE_QSPI` alone silently runs internal-only.
- App side: TG2 erase tests and the TC_Vtor skip now key on `_USE_XSPI` (was `_USE_OSPI_B`); TG2 setup calls new `rm_mcuboot_port_qspi_test_setup()` (data.c; pins P3_06/05/07-10, open QSPI, exit QPI 0xF5, reset 66/99, no image copy). Do NOT include `r_qspi_test_port.h` in data.c: it declares `extern qspi_extended_cfg_t g_qspi_extended_cfg` which clashes with data.c's static const. TG2 constants, requirement ids and anchors were renamed from `ospi` to `xspi` on 2026-10-07 (`XSPI_ERASE_TEST_*`, `mcuboot_port_xspi_*`, `um_mcuboot_port_xspi_*` in `!dsn/rm_mcuboot_port_usage_notes.md`); only `rm_mcuboot_port_ospi_test_setup()` (data.c, `test_files/src/r_tests_runner_main.c`) keeps the OSPI name because it is OSPI-specific.
- `ra6m5_ek` is already in the `rm_mcuboot_port` pipeline entry, so `ra6_qspi` runs there automatically.
- Unverified risks: (1) app xml `<align>128` vs QSPI page size 256 and `MCUBOOT_BOOT_MAX_ALIGN` = 128 (HP flash write size); `flash_area_align()` returns 256 for external, may trip MCUboot asserts. (2) MX25L quad-enable bit is assumed already set (same as legacy `qspi_test_setup_common`). (3) swap-mode scratch/erase semantics with QSPI not exercised. (4) The `bsp_linker_info.h` `BSP_PARTITION_QSPI_FLASH_BL_CPU0_S_*` entries in image variants were left as is.

## HARDWARE RESULT 2026-10-07 and ROOT CAUSE: the `*_qspi` linker variants do NOT affect flash_map (my earlier claims were wrong)
Result (EK-RA6M5 run of `ra6_qspi`): `TC_Erase_Rejects_Unaligned_Length` (tg2.c:246) and `TC_Erase_Rejects_Unaligned_Address` (tg2.c:269) FAIL with "Expected Not-Equal"; the other TG2 tests did not fail.
Root cause: `bsp_linker_info.h` (holds `flash_map[]`) is found through the COMPILE include path. That path comes from the shared xml of the project type: `test_files/shared/common_boot.xml` -> `.../!linker/${COMPILER}/${CORE_SUBFOLDER}boot`, `common_boot_app.xml` -> `.../image`. A project's `<linker_includes>` only changes the LINKER search path (`LIBINCPATH`, `SConstruct` ~1811), and a project's `<include_dirs>` is appended AFTER the common one, so `image_qspi`/`boot_qspi` lose to `image`/`boot` (verified from `scons -n` output: -I order boot_app, image, image_qspi; even adding the variant to `<include_dirs>` does not help and was reverted). Therefore both the app and the bootloader were compiled with the INTERNAL-flash flash_map: the secondary slot was really internal flash at 0x40000, QSPI was only opened/copied to, and `flash_area_erase` took the internal path, which accepts unaligned erases (returns 0). The reject checks exist only in the XSPI/external path of `flash_map.c` (`FSP_ERR_INVALID_SIZE`). Same reason the partial/other TG2 tests did not fail. The "1154 bytes bss proves XSPI path" evidence only showed the XSPI macro compiled the buffers, not that the external flash map was used.
How existing variants work: they are separate PROJECT TYPES with their own common xml and class in `SConstruct` (`boot_multi_images`/`boot_app_multi_images` -> `common_boot_multi_images.xml`, include+linker both `image_multi_images`); `mmf`/`xip` only change linker addresses, flash_map stays default. ra8d1 OSPI instead rewrote its default `boot`/`image` folders.
Fix options (user decision pending): (1) new project types `boot_qspi` + `boot_app_qspi` with shared xml and SConstruct class entries (repo-native, changes shared build script); (2) rewrite ra6m5 default `boot`/`image` like ra8d1 (breaks `ra6m5_std`, which needs the internal map); (3) source-level selection of the flash map inside `flash_map.c` (touches production port code).

## FIX APPLIED 2026-10-07 (verified by build + compiled-table dump, NOT yet re-run on hardware)
The flash_map problem above was fixed without touching `SConstruct`: the default `ra6m5/!linker/{gcc,ac6,iar,llvm}/{boot,image}/bsp_linker_info.h` (8 files) now guard the `FLASH_AREA_0S_ID` entry with `#ifdef RM_MCUBOOT_PORT_CFG_SECONDARY_USE_XSPI` -> `FLASH_DEVICE_EXTERNAL_FLASH`, `fa_off = BSP_PARTITION_QSPI_FLASH_CPU0_S_START` (0x60000000), else the old internal entry. Only the QSPI projects define the XSPI macro, so other ra6m5 projects are unchanged. The linker side still comes from the `boot_qspi`/`image_qspi` variants through `<linker_includes>`; the `bsp_linker_info.h` copies inside the `*_qspi` folders are never compiled (the compile path always uses the default folder) and are kept only for reference.
Verification (gcc, `arm-none-eabi-objdump -s flash_map.o`, entry = id,dev,pad,off,size): secondary app, typical app, boot `ra6_qspi` typical and overwrite all show entry 2 = `02 80 .. 00 00 00 60 ..` (external, 0x60000000); `rm_mcuboot_app` (used by `ra6m5_std`) still shows `02 7f .. 00 00 04 00` (internal 0x40000). `scons --build=rm_mcuboot_port --board=ra6m5_ek --project=ra6_qspi --compiler=gcc` and `--build=rm_mcuboot_app_qspi` exit 0 (the earlier shake.h link error did not recur in this checkout). How to re-check the compiled table: `arm-none-eabi-objdump -s build/<module>/ra6m5_ek/gcc/<build dir>/ra/fsp/src/rm_mcuboot_port/flash_map.o`, section `.rodata.flash_map`, 12 bytes per entry, device 0x7f internal / 0x80 external.

## ra6_qspi test flow (design, not yet run on hardware)
1. Build: boot `ra6_qspi` (swap default, `overwrite`, `overwrite_fast`; `boot_qspi` linker) + app `rm_mcuboot_app_qspi` (typical v1.0.0 primary; secondary v1.0.1, `RM_MCUBOOT_PORT_SECONDARY=1`, signed `--confirm`; `image_qspi` linker).
2. Flash (fsp_test_parallel, J-Link): typical signed srec -> internal 0x20000; secondary signed srec -> internal 0x40000 (staging only); bootloader -> 0x0. Loader never touches QSPI, hence no J-Link script (unverified on hardware; if loader reports size 0, add one like `SetupOSPI.JLinkScript`).
3. Boot (`test_files/src/r_tests_runner_main.c`, `TEST_MCUBOOT`): `qspi_test_setup_common()` opens QSPI, exits QPI (0xF5), resets flash (0x66/0x99), erases 0x20000 in 32KB, copies 0x20000 bytes from internal 0x40000 to QSPI 0x60000000; mbedTLS platform setup; `boot_go()`.
4. MCUboot: reads primary (internal 0x20000, v1.0.0) and secondary (QSPI 0x60000000, v1.0.1, memory-mapped reads via flash_map external entry), verifies EC256 signature, secondary newer+confirmed so it overwrites the primary in 32KB virtual sectors (swap config uses scratch `__BL_S` at 0x60000).
5. `RM_MCUBOOT_PORT_BootApp`: VTOR=0x20200, flush buffers, close flash/QSPI, jump.
6. App (secondary build now in primary slot) runs `RunAllRM_MCUBOOT_PORTTests`: TG1 `TC_Vtor` skipped (XSPI); TG2 per test calls `rm_mcuboot_port_qspi_test_setup()` then `flash_area_open(secondary)`: virtual sectors == 32KB, erase one block, erase multiple, partial-erase (ignored, 32KB == logical size), reject unaligned length, reject unaligned address.
Pass/fail linkage: if the update failed the old typical image runs (`RM_MCUBOOT_PORT_SECONDARY=0`) and TG2 fails with "Primary app running, expected secondary."

## Gotchas / open observations
- `rm_mcuboot_port` module constraints still reference `config.driver.psa_crypto.*` (v3 ids) for the PLATFORM_MEMORY and MEMORY_BUFFER_ALLOC checks, guarded by `testExists(interface.driver.psa_crypto)`. With the v4 tf_psa_crypto module (provides `interface.driver.tf_psa_crypto`) those checks are skipped, so v4 gets no equivalent check. Not changed.
- `ra8_ospi` has not been ported to v4 (uses v3 psa_crypto paths).
- Primary and secondary images are separate builds of `rm_mcuboot_app`; the `secondary` macro configuration sets `RM_MCUBOOT_PORT_SECONDARY=1`.
- **App linker scripts (image_qspi) should NOT define secondary slot at XSPI** (2026-10-09): Both primary and secondary apps use `image_qspi`, but the secondary slot symbols are bootloader-only. The app linker's `__BL_0_S_H/I_START` must stay at internal Flash (0x40000), not QSPI (0x60000000), even though the bootloader's corresponding `boot_qspi` defines it at QSPI. The flash_map is populated from `bsp_linker_info.h` at compile time; the app never uses it. When image_qspi incorrectly pointed secondary to QSPI, the binary would reference non-existent memory regions, causing hangs during flash or boot.
